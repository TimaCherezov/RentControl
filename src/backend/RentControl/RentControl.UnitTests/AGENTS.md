# Юнит-тесты

## Назначение

Юнит-тесты проверяют только модель — чистую логику без инфраструктуры: сущности, валидацию, вычисления (`Main.Model`, `Payments.Model`, `Realtime.Model`). Сами сервисы (`Main.Api`, `Payments.Api`, `Realtime.Api`, `Main.Worker`) на этом уровне не тестируются — для них есть интеграционные тесты и e2e.

Если тесту нужны БД, брокер, HTTP или запущенный сервис — это не юнит-тест, он относится к другому уровню пирамиды (см. [RentControl.E2ETests/AGENTS.md](../RentControl.E2ETests/AGENTS.md)).

## Структура

- `MainTests/` — тесты `Main.Model`;
- `PaymentsTests/` — тесты `Payments.Model`;
- `RealtimeTests/` — тесты `Realtime.Model`.

Тестовый файл лежит в папке той модели, которой принадлежит тестируемый класс.

## Правила

### Один тест — один сценарий

Юнит-тест покрывает ровно один тестовый сценарий: одно действие и один ожидаемый исход. Два сценария — два теста. Несколько ассертов в одном тесте допустимы, только пока они проверяют этот один исход.

### Канон юнит-теста

- Arrange–Act–Assert: подготовка данных, одно действие над тестируемым кодом, проверка результата.
- Проверяем наблюдаемое поведение — результат метода или исключение, а не приватное состояние объекта.
- Ожидаемое значение — константой. Логики в тесте быть не должно: `if`, циклы, вычисление ожидаемого результата — признак того, что тест проверяет сам себя.
- Тест изолирован и детерминирован: не зависит от порядка выполнения, данных других тестов, сети, БД и текущего времени.
- Повторяющиеся кейсы — через `[Theory]` + `[InlineData]`, а не копипастой тестов.

### Нейминг тестов

`МетодКоторыйТестируем_ПриКакихУсловиях_ЧтоДолжноБыть`.

Пример: `GetUser_WhenInvalidId_NotFound` (условный пример, не реальный сценарий).

### Тестовые классы

Один тестовый класс на один тестируемый класс: `Payment` → `PaymentTests`.

### Тестовые данные

Создание и заполнение тестовых данных выносим в TestDataBuilders (например, `PaymentBuilder`). В теле теста объекты руками не собираем — только билдер с точечными переопределениями:

```csharp
var payment = new PaymentBuilder().WithStatus(PaymentStatus.Paid).Build();
```

### Моки

Для изоляции зависимостей можно использовать Moq.

## Чеклист перед PR

- [ ] Тест проверяет модель, а не сервис.
- [ ] Один сценарий на тест: Arrange–Act–Assert, без логики в тесте.
- [ ] Нейминг: `Метод_ПриКакихУсловиях_Результат`.
- [ ] Один тестовый класс на тестируемый класс, файл в папке нужной модели.
- [ ] Тестовые данные — через билдеры, не собраны руками в тесте.
