# E2E-тесты

## Назначение

E2E-тесты проверяют межсервисное взаимодействие: сценарий проходит через несколько сервисов по реальному HTTP с реальной инфраструктурой (Postgres, RabbitMQ). Соседние сервисы не мокаются — если хочется замокать соседний сервис, значит тест относится к другому уровню пирамиды.

Уровни пирамиды:

- **юнит** — бизнес-логика внутри сервиса;
- **интеграционные** — сам сервис и его зависимости (БД, брокер);
- **e2e** — межсервисное взаимодействие.

E2E ловит то, что не видно тестам отдельных сервисов: рассинхрон контрактов на стыках, ошибки конфигурации (ключи подписи токенов, куки), проблемы миграций на реальной БД.

## Когда писать e2e

Пиши e2e, когда:

- сценарий пересекает границу сервисов (сервис A вызывает сервис B, событие из A обрабатывается в B);
- нужно зафиксировать публичный контракт между сервисами: при изменении одной стороны тест должен краснеть у другой;
- ключевой пользовательский путь проходит через несколько сервисов от начала до конца.

Не пиши e2e:

- проверяется бизнес-логика внутри одного сервиса → юнит-тест этого сервиса;
- проверяется сервис вместе с его зависимостями (БД, брокер, миграции) → интеграционный тест этого сервиса;
- нужны десятки комбинаций входных данных → юнит-уровень, e2e-прогон слишком дорогой.

Эвристика: взаимодействие сервисов → e2e; сервис + его зависимости → интеграционный; логика внутри одного сервиса → юнит.

## Инфраструктура

Сейчас один профиль запуска: тесты поднимают приложение через Aspire AppHost, по умолчанию стартуют Main.Api и Payments.Api, плюс Postgres (базы `maindb`, `paymentsdb`). При необходимости набор сервисов можно изменить параметром `Services`.

> **Правило:** если изменил инфраструктуру тестов (состав сервисов, контейнеры, схема подъёма, зависимости) — обнови этот раздел: что теперь поднимается и как.

## Технические правила

### Запуск приложения

- Приложение поднимается только через `DistributedApplicationTestingBuilder.CreateAsync<Projects.RentControl_AppHost>()`. Ручной запуск Kestrel, docker compose и т.п. в тестах запрещён.
- Одна общая фикстура на все тесты (xUnit collection fixture + `IAsyncLifetime`): старт стека дорогой, приложение не пересоздаётся на каждый тест-класс.
- Готовность сервисов ожидается только через `WaitForResourceHealthyAsync` с таймаутом и `CancellationToken`. Никаких `Thread.Sleep` и бесконечных ожиданий.
- У сервисов должны быть настроены health checks — иначе ожидание healthy не гарантирует готовность принимать запросы.
- Миграции БД накатываются явно в фикстуре до запуска тестов.
- В AppHost зависимости сервисов объявляются через `WaitFor` / `WaitForStart`, чтобы старт был детерминированным.

### HttpClient и адреса

- Адреса сервисов — только через `app.GetEndpoint(...)` или `app.CreateHttpClient(...)`. Захардкоженные порты и URL запрещены: Aspire рандомизирует порты.
- На HttpClient настраивается resilience handler (`AddStandardResilienceHandler`) — ретраи сглаживают флак на старте сервисов.
- HTTP-вызовы принимают `TestContext.Current.CancellationToken`.

### Данные и изоляция

- Каждый тест создаёт свои данные с уникальными идентификаторами (например, `e2e-{Guid:N}@test.local`). Тесты не зависят от порядка выполнения и от данных друг друга.
- Билдеры тестовых данных и другие хелперы генерации данных выносятся в отдельные классы, пригодные для переиспользования между сценариями. Не дублировать генерацию данных внутри тестов.

### Читаемость

- Один файл — одна группа взаимосвязанных сценариев. Создание внутренних объектов сценарий - приватные хелперы. Создание объектов, которые нужно и в других тестах - переиспользуемые утилиты либо TestDataBuilder.
- Ассерты с сообщениями, указывающими на то, что именно пошло не так: «Main не вернул accessToken», а не просто упавший assert.
